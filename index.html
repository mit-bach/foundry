Client applications of agents

Agents that work in the tools a company already has.

We build a company their own application, then we keep it running. The company uses that application. When it cannot do something, it asks the Foundry. We change the system, prove the change away from live accounts, and ship it back.

  • Their application The client never operates the Foundry. They use the application we deployed for them.
  • Their tools Mail, books, scheduling, and the old screen with no connector stay where they are.
  • One kernel The same small harness runs every client. A new client is a new set of files.

What we are doing

A small company already has a way of working. The Tuesday morning job happens in software they paid for years ago, including software that was never meant to be called by another program.

The Foundry puts agents inside that work. An adapter connects a tool that already has a connector. Where there is no connector, an agent learns one task on the real screen, writes the skill from a run that succeeded, and hands that skill to the bot that will own the system.

Skills start empty. They are filled from work that actually happened. A skill is allowed to change when the steps stop working. A repeated break comes back to the Foundry as a ticket, and the repair is checked again before it reaches every client that uses it.

What the company sees

Their site shows what happened, what is waiting, and what an agent will not do without an answer. A question can be a choice, or their own words.

  • Run. The action is already allowed.
  • Ask. The agent waits.
  • Yes, and always. A repeated answer becomes the policy on that action.

Anything that sends, pays, or deletes sits behind a gate. After the design is accepted, the questions live on the site. The client is not handed code.

How a system is made

  1. Intake. The meeting, plus the tools, logins, and documents they already have.
  2. Business. Who they are, what they want, and what they use.
  3. Design. The agents, the adapters, and the gates.
  4. Check. The design is a file. A program checks it before a build starts.
  5. Build. Prompts, adapters, and the client site.
  6. Eval. A sandbox. A stand-in plays the outside world. Live accounts stay untouched.
  7. Deploy. One live copy. A change is tried beside it before it replaces the live one.
  8. Maintain. A break comes back as a ticket. The repair is evaluated again, then sent to each client it applies to.

Only the live instance may touch the world. A sandbox holds no live password. A change that fails one client's checks is not pushed to that client.

Where it is

We are building this for a few real clients. The harness, the client site, and the first adapters are in use on real tasks, including work in software that has no connector.
